# 조회수 증가 DB원자적 증가 vs Redis write-back

## 질문

트래픽이 많을때는 redis를 이용한 write-back방식이 유리한가?

유리하다면, 어느정도 트래픽에서 성능을 발휘하며 그 성능이 얼마나 되는지

---

## 측정 기준

### k6
- p99 - 500ms 미만
- 에러율 - 1% 미만
- dropped_iterations - 0을 목표로
    - 서버 지표가 정상인 상태에서 극소량 발생하면 측정 오차로 판단

### 서버, DB 지표
- 커넥션 풀 대기 - 지속되지 않음

---

## 측정 방법

`ramping-arrival-rate`로 한계구간을 찾은 뒤, 그 구간에서 RPS별로 `constant-arrival-rate` 를 따로 돌려 한계값을 확정한다.

---

### 최종 비교 표

| 구분 | db | buffered |
| --- | --- | --- |
| 합격 확인 | 600 RPS | 3500 RPS |
| 경계 | 700 RPS | 4000 RPS |
| 불합격 | 800 RPS 이상 | 5000 RPS  |
| 병목 모양 | 락 대기 7~9, 풀 포화 | 락 대기 0, DB는 한가한데 풀 포화 (앱 쪽 원인 미확인) |
| 한계 | 약 600~700 | 약 3500~4000 |

---

## 결론

1. DB 방식의 한계는 약 600~700 RPS이고, 같은 행 UPDATE의 락 대기와 풀 포화로 나타났다.
2. Redis 방식은 약 3500~4000 RPS에서 풀 포화가 나타났지만 락 대기는 전 구간 0이였다. 서버쪽 병목을 해결하면 한계 RPS가 더 높아질 것으로 예상된다.
3. 같은 행에 쓰기 트래픽이 몰릴 때는 요청마다 UPDATE하는 것보다 Redis에 모았다가 반영하는 방식이 처리량 측면에서 크게 유리했다.

## 한계점

---

- 단일 PC실험
    - 서버, Redis, DB, k6 모두 동일 환경
- 하나의 행에만 몰린 시나리오
- buffered 방식의 병목 원인은 미확인
    - 풀 포화이지만 DB 락대기 0, DB실행세션 1~5로 여유
    - 서버쪽 병목으로 추정
